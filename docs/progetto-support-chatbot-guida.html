Assistente di Supporto Tecnico RAG-based

Un chatbot di supporto che indicizza documentazione interna, risponde con Azure OpenAI usando RAG per il grounding, ed esegue escalation verso un sistema di ticketing quando non trova la risposta.

Setup

Fondamenta Azure

Prepari il terreno prima di scrivere codice: un resource group dedicato, un Key Vault, e un budget alert.

Come si fa, passo dopo passo

  1. Crea il Resource Group. Vai su portal.azure.com e fai login. Cerca "Resource groups" → + Create. Subscription tua, nome rg-support-chatbot-dev, region "West Europe". Review + create → Create. Un Resource Group è solo un contenitore logico: raggruppa le risorse del progetto così puoi vederle, gestirle ed eliminarle tutte insieme.
  2. Crea il Key Vault. Cerca "Key Vault" → + Create. Resource group appena creato, nome univoco globale (es. kv-supportchatbot-don), region uguale, pricing tier "Standard". Review + create → Create.
  3. Imposta un budget di sicurezza. Cerca "Cost Management + Billing" → Budgets → + Add. Scope: la subscription. Importo (es. 20€/mese). Avviso email all'80% e al 100%. Salva.

Cosa costruisci in questa fase

Nessun codice qui, ma tre fondamenta su cui si appoggia tutto il resto: il Resource Group è il contenitore che terrà insieme ogni risorsa del progetto, comodo per vederle e cancellarle tutte insieme a fine esperimento; il Key Vault è pronto per il giorno in cui servirà davvero un segreto (oggi non ne abbiamo ancora nessuno, perché tutto quello che costruiremo userà Managed Identity al suo posto); il budget alert è la rete di sicurezza per tutte le fasi successive, incluse quelle che costano davvero qualcosa (Azure OpenAI in Fase 2).

# domain/interfaces.py
from typing import Protocol

class ILLMClient(Protocol):
    def complete(self, prompt: str, context: list[str]) -> str: ...

class IRetriever(Protocol):
    def retrieve(self, query: str) -> list[str]: ...
# services/chat_service.py
from domain.interfaces import ILLMClient, IRetriever

class ChatService:
    def __init__(self, retriever: IRetriever, llm: ILLMClient):
        self._retriever = retriever
        self._llm = llm

    def handle(self, message: str) -> str:
        context = self._retriever.retrieve(message)
        return self._llm.complete(message, context)
# function_app.py — versione completa di questa fase
import azure.functions as func
import json
from services.chat_service import ChatService
from domain.interfaces import ILLMClient, IRetriever

app = func.FunctionApp()


class EchoLLMClient(ILLMClient):
    """Finto LLM: ripete il messaggio. Lo sostituiamo con Azure OpenAI in Fase 2."""
    def complete(self, prompt: str, context: list[str]) -> str:
        return f"hai detto: {prompt}"


class EmptyRetriever(IRetriever):
    """Nessun contesto per ora. Lo sostituiamo con Azure AI Search in Fase 3."""
    def retrieve(self, query: str) -> list[str]:
        return []


chat_service = ChatService(retriever=EmptyRetriever(), llm=EchoLLMClient())


@app.route(route="chat", auth_level=func.AuthLevel.ANONYMOUS)
def chat(req: func.HttpRequest) -> func.HttpResponse:
    body = req.get_json()
    message = body.get("message", "")
    reply = chat_service.handle(message)
    return func.HttpResponse(
        json.dumps({"reply": reply}),
        mimetype="application/json",
        status_code=200
    )

Cosa costruisci in questa fase

domain/interfaces.py non contiene logica, solo due contratti: ILLMClient dice "qualcosa che sa rispondere a un prompt dato un contesto", IRetriever dice "qualcosa che sa recuperare contesto data una query". Nessuno dei due sa come farlo — è deliberato.

services/chat_service.py è la logica di dominio vera. ChatService non sa se il suo llm è Azure OpenAI, un finto eco, o domani qualcos'altro: conosce solo l'interfaccia. È la Dependency Inversion applicata concretamente, non solo citata.

function_app.py fa tre cose distinte: definisce due implementazioni finte delle interfacce (EchoLLMClient, EmptyRetriever), costruisce chat_service iniettandole, ed espone la funzione chat col decoratore @app.route — quel decoratore è il trigger. La function stessa fa solo da adapter, zero logica di business: è il Single Responsibility Principle, visibile nel codice invece che solo enunciato. In Fase 2 basterà cambiare una riga (llm=EchoLLMClient() → llm=AzureOpenAIClient(...)) senza toccare il resto.

Cosa succede, passo dopo passo, quando arriva una richiesta

  1. Il runtime di Azure Functions riceve la richiesta HTTP su /api/chat → il trigger (@app.route) si attiva → chiama chat(req).
  2. chat() legge il body JSON ed estrae message.
  3. Chiama chat_service.handle(message).
  4. ChatService.handle() chiama prima self._retriever.retrieve(message) — oggi è EmptyRetriever, ritorna sempre [].
  5. Poi chiama self._llm.complete(message, context) — oggi è EchoLLMClient, ritorna "hai detto: {message}".
  6. chat() impacchetta la risposta in JSON e la restituisce con status 200.

Azure OpenAI

Collegare il modello

Crei la risorsa Azure OpenAI, deployi un modello, e sostituisci EchoLLMClient con una chiamata reale — autenticata con Managed Identity.

Come si fa, passo dopo passo

  1. Crea la risorsa Azure OpenAI. "Create a resource" → cerca "Azure OpenAI" → Create. Resource group della Fase 0. Region: verifica prima su "Azure AI Foundry model availability" quali region hanno il modello scelto. Pricing tier: Standard S0.
  2. Deploya un modello. Apri la risorsa → link "Go to Azure AI Foundry portal" → Deployments → + Create new deployment. Modello: gpt-4o-mini. Nome deployment: chat-deploy.
  3. Assegna una Managed Identity alla Function App. Sulla Function App → Identity → tab System assigned → On → Save → conferma.
  4. Dai a quella identità il permesso di chiamare Azure OpenAI. Sulla risorsa Azure OpenAI → Access control (IAM) → + Add → Add role assignment → ruolo "Cognitive Services OpenAI User" → Next → "Managed identity" → + Select members → la tua Function App → Review + assign.
  5. Installa i pacchetti Python. 
    pip install openai azure-identity
pip freeze > requirements.txt
  6. Crea infrastructure/azure_openai_client.py (nuova cartella, stesso livello di domain/ e services/, con __init__.py) col codice sotto.
  7. In function_app.py, cambia una riga sola: llm=EchoLLMClient() diventa llm=AzureOpenAIClient(endpoint="...", deployment="chat-deploy").
  8. Testa in locale. Attenzione: in locale DefaultAzureCredential usa la tua identità (quella di az login), non la Managed Identity — che esiste solo su Azure. Assicurati quindi che anche il tuo utente abbia il ruolo "Cognitive Services OpenAI User" sulla risorsa (stesso passo IAM di sopra, stavolta scegli "User" e seleziona te stesso).
  9. Ridistribuisci con "Deploy to Function App", poi testa l'endpoint pubblico.
# infrastructure/azure_openai_client.py
from azure.identity import DefaultAzureCredential, get_bearer_token_provider
from openai import AzureOpenAI
from domain.interfaces import ILLMClient

class AzureOpenAIClient(ILLMClient):
    def __init__(self, endpoint: str, deployment: str):
        token_provider = get_bearer_token_provider(
            DefaultAzureCredential(),
            "https://cognitiveservices.azure.com/.default"
        )
        self._client = AzureOpenAI(
            azure_endpoint=endpoint,
            azure_ad_token_provider=token_provider,
            api_version="2024-10-21",
        )
        self._deployment = deployment

    def complete(self, prompt: str, context: list[str]) -> str:
        system = "Rispondi solo usando il contesto fornito. Se non basta, dillo esplicitamente."
        messages = [
            {"role": "system", "content": f"{system}\n\nContesto:\n{chr(10).join(context)}"},
            {"role": "user", "content": prompt},
        ]
        result = self._client.chat.completions.create(model=self._deployment, messages=messages)
        return result.choices[0].message.content

Cosa costruisci in questa fase

infrastructure/azure_openai_client.py è la prima implementazione reale di ILLMClient — get_bearer_token_provider ottiene un token da Microsoft Entra ID invece di usare una API key, ed è ciò che rende possibile l'autenticazione via Managed Identity. Sostituendo llm=EchoLLMClient() con llm=AzureOpenAIClient(...) in function_app.py, tutto il resto (ChatService, l'endpoint, il decoratore) resta identico: è esattamente il beneficio della dependency inversion impostata in Fase 1.

Cosa succede, passo dopo passo

  1. Come in Fase 1, fino a self._llm.complete(message, context) — ma ora self._llm è AzureOpenAIClient.
  2. get_bearer_token_provider chiede un token valido a Microsoft Entra ID, usando l'identità disponibile (Managed Identity su Azure, il tuo utente in locale).
  3. Il client chiama l'endpoint del deployment su Azure OpenAI, passando il messaggio e il contesto (per ora vuoto, arriva in Fase 3).
  4. Azure OpenAI risponde col testo generato dal modello, che torna su fino al chiamante HTTP.

RAG

Pipeline di retrieval

Dai al bot una base di conoscenza reale, indicizzata su Azure AI Search con ricerca ibrida, e sostituisci EmptyRetriever con una vera implementazione.

Come si fa, passo dopo passo

  1. Crea la risorsa Azure AI Search. "Create a resource" → "Azure AI Search" → Create. Resource group della Fase 0. Pricing tier Free (limite: 1 indice, 50MB — sufficiente per l'esperimento).
  2. Prepara i documenti FAQ. Cartella knowledge-base/ nel progetto, 5-10 file .md con FAQ inventate ma realistiche.
  3. Deploya un modello di embedding. Azure AI Foundry → Deployments → + Create new deployment → text-embedding-3-small. Nome deployment embed-deploy.
  4. Crea l'indice. Sulla risorsa Azure AI Search → Import and vectorize data → segui il wizard: sorgente dati (puoi caricare i file direttamente), modello di embedding da usare.
  5. Verifica. Sulla stessa risorsa → Search explorer → prova una query, dovresti vedere i tuoi documenti tra i risultati.
  6. Crea infrastructure/azure_search_retriever.py col codice sotto.
  7. In function_app.py, cambia un'altra riga: retriever=EmptyRetriever() diventa retriever=AzureSearchRetriever(endpoint="...", index_name="...").
  8. Testa end-to-end. Fai una domanda che corrisponde a una FAQ e verifica che la risposta finale citi quel contenuto.
# infrastructure/azure_search_retriever.py
from azure.search.documents import SearchClient
from azure.identity import DefaultAzureCredential
from domain.interfaces import IRetriever

class AzureSearchRetriever(IRetriever):
    def __init__(self, endpoint: str, index_name: str):
        self._client = SearchClient(endpoint, index_name, DefaultAzureCredential())

    def retrieve(self, query: str) -> list[str]:
        results = self._client.search(search_text=query, top=3, query_type="semantic")
        return [r["content"] for r in results]

Cosa costruisci in questa fase

infrastructure/azure_search_retriever.py è la prima implementazione reale di IRetriever. Sostituendo retriever=EmptyRetriever() con retriever=AzureSearchRetriever(...), ChatService inizia a passare contesto vero al modello invece di una lista vuota — di nuovo, senza toccare ChatService stesso. I file .md in knowledge-base/ non entrano nel deploy della Function App: servono solo allo script/wizard di indicizzazione, una tantum, per popolare l'indice su Azure AI Search.

Cosa succede, passo dopo passo

  1. ChatService.handle() chiama ora AzureSearchRetriever.retrieve(message) invece del retriever vuoto.
  2. Azure AI Search cerca i chunk più rilevanti (ricerca semantica/ibrida) e li ritorna come lista di stringhe.
  3. Quella lista diventa context, passato ad AzureOpenAIClient.complete() e inserito nel prompt di sistema.
  4. Il modello risponde "ancorato" a quel contesto invece di inventare — è il grounding.

Problemi comuni

Application Insights

Osservabilità e troubleshooting

Instrumenti la pipeline, poi fai l'esercizio più importante: rompi qualcosa di proposito e lo risolvi solo dai log.

Come si fa, passo dopo passo

  1. Collega Application Insights. Sulla Function App → Application Insights → Turn on Application Insights → crea nuova risorsa (stesso resource group) → Apply.
  2. Installa il pacchetto. 
    pip install azure-monitor-opentelemetry
pip freeze > requirements.txt
  3. Crea infrastructure/app_insights_telemetry.py con un helper minimale che registra un evento custom (durata retrieval, token, esito).
  4. Richiama l'helper dentro ChatService, subito dopo ogni step.
  5. Genera traffico. 5-10 richieste diverse.
  6. Interroga i log. Sulla risorsa Application Insights → Logs → chiudi la finestra di esempi se appare → scrivi: 
    traces
| where timestamp > ago(1h)
| order by timestamp desc
| take 50
  7. Esercizio di troubleshooting. In azure_search_retriever.py, aggiungi temporaneamente: 
    import time
def retrieve(self, query: str) -> list[str]:
    time.sleep(15)
    raise TimeoutError("Simulazione timeout su Azure AI Search")
    Ridistribuisci, fai una richiesta, poi trova l'eccezione: 
    exceptions
| where timestamp > ago(15m)
| order by timestamp desc
    Rimuovi il bug e ridistribuisci di nuovo.

Cosa costruisci in questa fase

infrastructure/app_insights_telemetry.py non entra mai nel flusso di business — ChatService lo richiama solo per registrare cosa è successo (durata, token, esito), mai per decidere cosa fare dopo. È una responsabilità trasversale (cross-cutting concern) tenuta separata dalla logica principale, invece che sparsa dentro ogni metodo.

Cosa succede, passo dopo passo

  1. Ogni chiamata a ChatService.handle() genera più eventi: inizio/fine retrieval, inizio/fine chiamata LLM, eventuale eccezione.
  2. L'SDK azure-monitor-opentelemetry li spedisce ad Application Insights in background, senza bloccare la risposta all'utente.
  3. Nel portale, i log diventano interrogabili con KQL entro qualche minuto dall'invio (non è istantaneo).

Problemi comuni

ErroreCausaSoluzione
Log query vuota subito dopo aver fatto una richiestaIngestion delay: i dati impiegano qualche minuto ad arrivareAspetta 2-5 minuti e riprova la query
Nessuna telemetria custom, solo quella di defaultLa connection string di Application Insights non è configurata nell'appVerifica che APPLICATIONINSIGHTS_CONNECTION_STRING sia tra le variabili d'ambiente della Function App

Elaborazione asincrona (simulando una CR)

Aggiungi una queue-triggered function per le richieste "complesse", senza toccare il flusso già esistente.

Come si fa, passo dopo passo

  1. Individua lo storage account della Function App (creato automaticamente in Fase 1, stesso resource group, nome tipo supportchatbotXXXX).
  2. Crea una coda. Apri lo Storage Account → Queues → + Queue → nome complex-queries.
  3. Azurite deve essere acceso (stesso comando azurite della Fase 1, in un terminale a parte).
  4. Crea la nuova function. 
    func new
    Scegli "Azure Queue Storage trigger", nome process_complex_query, coda complex-queries.
  5. Modifica l'endpoint /api/chat: aggiungi un controllo semplice (es. lunghezza del messaggio) — se "complessa", scrivi un messaggio sulla coda e rispondi 202 Accepted con un ID di richiesta, invece di rispondere subito.
  6. Scrivi la logica della queue-triggered function: legge il messaggio, chiama chat_service.handle() come prima, salva/logga il risultato.
  7. Testa in locale con func start (e Azurite acceso): manda una richiesta "complessa" e verifica nei log che la queue-function parta.

Cosa costruisci in questa fase

La nuova queue-triggered function (process_complex_query) importa e riusa lo stesso chat_service costruito in Fase 1 — non esiste una seconda copia della logica di dominio. L'unica modifica a function_app.py è dentro l'endpoint HTTP già esistente, per decidere se instradare verso la coda invece di rispondere subito: un'aggiunta, non una riscrittura.

Cosa succede, passo dopo passo

  1. L'endpoint HTTP riceve la richiesta, la valuta "complessa", scrive un messaggio JSON sulla coda complex-queries.
  2. Risponde subito al client con 202 — l'utente non resta in attesa.
  3. Il runtime nota il nuovo messaggio in coda e attiva process_complex_query in background, indipendentemente dalla richiesta HTTP originale.
  4. Quella function riusa lo stesso chat_service, identica logica, nessuna duplicazione.

Problemi comuni

ErroreCausaSoluzione
"Unable to access AzureWebJobsStorage" (di nuovo)Azurite non acceso — stesso problema della Fase 1Avvialo in un terminale a parte prima di func start
La queue-function non si attiva maiIl nome della coda nel decoratore non combacia esattamente con quello creatoControlla che i due nomi siano identici, inclusi maiuscole/minuscole

🎯 Perché per il colloquio

È Open/Closed Principle applicato architetturalmente: estendi il comportamento aggiungendo una function, senza modificare ChatService né l'endpoint esistente.

Widget e sistema enterprise

Un piccolo widget HTML/JS embeddabile, più uno stub di integrazione enterprise.

Come si fa, passo dopo passo

  1. Crea widget/chat-widget.html col codice sotto.
  2. Aprilo nel browser. Estensione VS Code "Live Server" → tasto destro sul file → Open with Live Server.
  3. Prova a mandare un messaggio. Se non succede nulla, apri la Console del browser (F12 → tab Console) e leggi l'errore.
  4. Se vedi un errore CORS — il browser blocca chiamate verso un altro dominio a meno che quel dominio non lo permetta esplicitamente — vai sulla Function App → CORS → aggiungi l'origine (es. http://127.0.0.1:5500 per Live Server, o * solo per test locali) → Save.
  5. Simula il sistema enterprise. Vai su webhook.site (gratuito, senza registrazione) — genera subito un URL unico. Copialo.
  6. Crea services/ticket_service.py che fa una POST a quell'URL quando manca contesto sufficiente.
  7. Verifica su webhook.site che la richiesta arrivi davvero.
<!-- widget/chat-widget.html (estratto) -->
<script>
async function sendMessage(text) {
  const res = await fetch("https://<la-tua-function>.azurewebsites.net/api/chat", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ message: text })
  });
  return res.text();
}
</script>

Cosa costruisci in questa fase

widget/chat-widget.html è volutamente fuori dal resto del repository Python: è un client indipendente che parla con la tua API solo via HTTP — potrebbe essere sostituito domani da un altro frontend qualsiasi senza toccare una riga di backend. services/ticket_service.py segue lo stesso principio delle altre integrazioni: un'implementazione concreta richiamata da ChatService solo quando serve l'escalation, non ovunque nel codice.

Costi e sottoscrizioni

PTU vs consumo

Non spendi soldi veri: è un esercizio di comprensione del modello di costo, da saper recitare a memoria in colloquio.

Come si fa, passo dopo passo

  1. Controlla il budget. "Cost Management + Billing" → Budgets → verifica che quello della Fase 0 sia ancora attivo.
  2. Guarda quanto hai speso. Stesso menu → Cost analysis → filtra per il resource group del progetto.
  3. Cerca i prezzi attuali di Azure OpenAI (pay-as-you-go) e delle PTU sulla pagina ufficiale Microsoft — i numeri cambiano nel tempo.
  4. Fai il calcolo comparativo con carta/Excel: stima richieste/mese realistiche, moltiplica per il costo a token, confronta col costo mensile fisso di un'unità PTU.

Cosa costruisci in questa fase

Nessun file di codice qui — è un esercizio di analisi, non di implementazione. Quello che ti porti via è un numero (la soglia di richieste/mese a cui converrebbe passare a PTU) e la capacità di argomentarlo, non un artefatto nel repository.

🪤 Trappola da colloquio

PTU ha senso solo con volume alto e prevedibile — è capacità riservata che paghi comunque, anche sotto-utilizzata. Con traffico variabile, pay-as-you-go resta quasi sempre la scelta più razionale.
